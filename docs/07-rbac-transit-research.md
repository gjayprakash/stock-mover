# 07 · Roles, transfer requests and driver tracking: research

Date: 2026-11-21 · Status: research only, nothing built · Supersedes the design in issue #19.

**Summary.** Build sign-in on our own stack (NestJS 11, `pg` on Neon). Use one global guard, a `@Roles()` decorator read through `Reflector`, server-side sessions in Postgres behind a `__Host-` cookie (HttpOnly, Secure, SameSite=Lax), an Origin / `Sec-Fetch-Site` check on writes, and scrypt password hashes from `node:crypto`. A seed script inserts the one super admin. Scope managers to their store in the app layer, not with Postgres RLS: most of our data sits in one `runs.moves_json` blob and CSV files, which RLS can't filter. Drivers pair through a single-use, short-lived token in the URL fragment. The manager sends it from their own phone with a `wa.me` click-to-chat link. The driver's tap POSTs the token, which is swapped for a long-lived, revocable device cookie. The driver app is a PWA for Phase 1, with a big "send my location" button pressed every 1–2 hours, icons, colours and Hindi audio. Live tracking in Phase 2 needs a native Android app with a location foreground service, because web pages get no location while hidden. It also needs a paid Render instance.

---

## Recommended MVP (Phase 1)

1. **Auth.** Tables `users`, `sessions`. `POST /api/auth/login|logout`, `GET /api/me`. One global `AuthGuard` plus `RolesGuard` as `APP_GUARD`. `@Public()` goes on `/api/health` and `/api/auth/*`. `POST /api/run` keeps its `CRON_SECRET`.
2. **Seed.** `scripts/seed-admin.ts` (email argument, password read from stdin, never from argv or the repo). It refuses to run if a super admin already exists.
3. **Admin screens.** Super admin creates store managers (email, name, location) and sees everything.
4. **Scoping.** A `Scope` (`{all:true}` or `{locationId}`) is resolved once per request and passed into every service query. The engine's `moves.json` is filtered after load.
5. **Transfers.** Manager screen "Request stock": pick SKU and qty. It shows the nearest locations that can spare stock under the five rules. Requests and shipments run through the lifecycle in section H. Each manager gets an "In / Out" list of transfers.
6. **Drivers.** The manager adds a driver (name, phone), taps "Send link on WhatsApp", the driver taps once and is paired. The driver sees only the shipments assigned to them, with three big buttons: Picked up / Send location / Delivered.
7. **Tracking.** `location_pings` from button taps. The manager sees the last ping, its age, and a red badge when there has been no ping for 2 h or more.

## Phase 2

A native Android driver app with a `location` foreground service posting every N seconds. The manager map uses Leaflet with OSM tiles, fed by Nest SSE. Render moves to a paid instance. Optional Postgres RLS as defence in depth. WhatsApp Cloud API for automatic messages.

## A. Auth and RBAC in NestJS

- **Guards are the right hook.** A guard implements `CanActivate`, runs after middleware and before interceptors and pipes, and has the `ExecutionContext`. When it returns `false`, Nest throws `ForbiddenException` (403). Registering a guard as an `APP_GUARD` provider makes it global *with* dependency injection. `app.useGlobalGuards()` can't inject. ([guards](https://docs.nestjs.com/guards))
- **Role metadata.** `export const Roles = Reflector.createDecorator<string[]>()` creates the decorator. The guard reads it with `reflector.getAllAndOverride(Roles, [context.getHandler(), context.getClass()])`, so a method-level value overrides the class-level one. ([execution context: reflection and metadata](https://docs.nestjs.com/fundamentals/execution-context#reflection-and-metadata), [guards: role-based authentication](https://docs.nestjs.com/guards))
- **The new official packages.** The Nest docs now describe `@nestjs/authentication` (sessions, scrypt `PasswordHasher`, API keys, CSRF handling) and `@nestjs/authorization` (policy classes, deny-by-default global guard). ([authentication](https://docs.nestjs.com/security/authentication), [authorization](https://docs.nestjs.com/security/authorization)) Both are version 0.1.x and declare `@nestjs/core ^12.0.0` as a peer dependency ([npm registry](https://registry.npmjs.org/@nestjs/authentication)). We are on Nest `^11.1.0` (`apps/api/package.json`). **Decision:** don't upgrade Nest for this. Hand-roll about 150 lines that copy the package's defaults, listed below, and revisit after the hackathon.
- **Session cookie, not JWT.** Nest serves the web app on the same origin (`app.module.ts`, ServeStatic), so a cookie needs no CORS and no token handling in JS. A server-side session row can be revoked at once on logout or when a manager is deactivated. OWASP requires server-side invalidation on logout and a new session ID after login ([Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Keep sessions in Postgres, not memory: Render Free spins the service down after 15 min idle and loses local state ([Render free](https://render.com/docs/free)).
- **Cookie.** Use `__Host-sid=<256-bit random>; HttpOnly; Secure; SameSite=Lax; Path=/`. HttpOnly hides it from `document.cookie`. Secure limits it to HTTPS, and MDN notes browsers except Safari make an exception for localhost. `__Host-` forces Secure, no Domain and `Path=/`. ([MDN cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)) OWASP asks for at least 64 bits of entropy and an explicit `SameSite=Strict|Lax` ([Session CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Store only SHA-256(token), which is what `@nestjs/authentication` does, so a leaked table can't be replayed ([authentication](https://docs.nestjs.com/security/authentication)). Use a 12 h absolute lifetime, matching #19 and inside OWASP's 4–8 h office-day example plus a margin.
- **CSRF.** `SameSite=Lax` still sends the cookie on cross-site top-level navigations with safe methods. It is "defense in depth", not a robust CSRF defence ([RFC 6265bis-22 §5.6.7.1](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.6.7.1)). OWASP: never change state with GET. Fetch Metadata (`Sec-Fetch-Site`) is "lightweight and reliable", and an Origin check is the mandatory fallback ([CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). **Decision:** a middleware rejects POST/PUT/PATCH/DELETE that carry the cookie when `Sec-Fetch-Site` is `cross-site` or `Origin` doesn't match the host. This mirrors `@nestjs/authentication` ([docs](https://docs.nestjs.com/security/authentication)).
- **Password hashing.** OWASP's order is Argon2id (m=19 MiB, t=2, p=1), then scrypt (N=2^17, r=8, p=1). bcrypt is legacy only, with a 72-byte input limit ([Password Storage CS](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). `crypto.argon2` exists only since Node **v24.7.0** ([Node crypto](https://nodejs.org/api/crypto.html#cryptoargon2algorithm-parameters-callback)), and `render.yaml` pins `NODE_VERSION: "22"`. `crypto.scrypt` has been built in since v10.5.0. Its default `maxmem` is 32 MiB, and it errors when `128*N*r > maxmem`, so N=2^17 needs `maxmem` ≥ 128 MiB, say 256 MiB ([Node crypto: scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)). **Decision:** use async scrypt with OWASP parameters, store `$scrypt$ln=17,r=8,p=1$salt$hash`, and compare with `timingSafeEqual`. No native dependencies. This is also what `@nestjs/authentication` ships ([docs](https://docs.nestjs.com/security/authentication)).
- **Seeding the super admin.** Run a one-off script against `DATABASE_URL`, reading the password from a hidden stdin prompt so it stays out of shell history. Enforce a single super admin with a partial unique index (`create unique index one_super_admin on users ((true)) where role = 'super_admin'`). Insert with `on conflict do nothing`, and print the email only. There is no sign-up route at all.

## B. Location scoping: app layer vs Postgres RLS

- **RLS facts.** After `ENABLE ROW LEVEL SECURITY`, a table with no policy is default-deny. Superusers and `BYPASSRLS` roles always bypass RLS. Table owners bypass it unless `FORCE ROW LEVEL SECURITY` is set. `USING` filters rows that are read, and `WITH CHECK` validates rows that are written. ([PG RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)) A per-request user can be passed with `set_config('app.location_id', $1, true)`. With `is_local=true` it lasts only for the current transaction, and policies read it back with `current_setting(name, true)` ([PG admin functions](https://www.postgresql.org/docs/current/functions-admin.html)).
- **Pooling.** Neon's pooler is PgBouncer in **transaction mode**, and session `SET`/`RESET` is unsupported. Transaction-scoped settings (`SET LOCAL`) are the documented workaround ([Neon pooling](https://neon.com/docs/connect/connection-pooling)). node-postgres: never run transactions through `pool.query`; check out one client ([node-postgres transactions](https://node-postgres.com/features/transactions)). Our `DbService.query()` uses `pool.query` for everything (`apps/api/src/db/db.service.ts`), so RLS would mean wrapping every request in `BEGIN; select set_config(...,true); ...; COMMIT` on one client.
- **Roles.** Neon roles created in the console or API are members of `neon_superuser`, which carries `BYPASSRLS` in projects created after Aug 2023. Roles made with SQL `CREATE ROLE` get only basic privileges ([Neon roles](https://neon.com/docs/manage/roles)). The app would need a new non-owner SQL role and a second connection string.
- **Recommendation: app layer.** The decisive fact is that the data a manager reads is mostly not rows. `moves.json` is one `jsonb` per run (`runs.moves_json`, `db.service.ts`), and catalogue and stock come from CSV files in memory. RLS can't filter inside either. So: one `ScopeService` builds `Scope` from `request.user`. Every repository function takes it and adds `location_id = $n` or `(from_location = $n or to_location = $n)`. `MovesController` filters `moves`, `stores` and `problems` by location before responding. Controllers never take a `location_id` from the client for managers. Tradeoff: one forgotten filter leaks data, so the scope argument is *required* by the function signatures. RLS is a Phase 2 add-on for the new transfer tables only.

## C. Driver pairing via link

- **Pattern.** RFC 8628 (device grant) issues a short-lived `user_code` / `verification_uri_complete` (meant for "non-textual transmission") with `expires_in` ([§3.2](https://datatracker.ietf.org/doc/html/rfc8628#section-3.2)). It warns about brute force, so rate-limit attempts and keep validity short ([§5.1](https://datatracker.ietf.org/doc/html/rfc8628#section-5.1)). It also warns about "remote phishing", where a code is forwarded to someone else, so the approver should confirm which device was paired ([§5.4](https://datatracker.ietf.org/doc/html/rfc8628#section-5.4)). Our flow is the reverse direction (link → phone), but the same controls apply.
- **Token rules.** OWASP: generate URL tokens with a CSPRNG, make them long enough to resist brute force, single-use, and expiring, store them securely, and send `Referrer-Policy: no-referrer` on the landing page ([Forgot Password CS](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)). Use 32 random bytes in base64url, store only SHA-256, and expire after 30 min.
- **Link-preview bots.** WhatsApp's own docs: "WhatsApp crawls the web page via an HTTP GET request" to build a preview, with User-Agent `WhatsApp/2.x.x.x A|I|N` ([WhatsApp link previews](https://developers.facebook.com/documentation/business-messaging/whatsapp/link-previews)). Whether the crawl comes from the sender's phone or Meta's servers is **unconfirmed**. RFC 9110: GET is safe so that "spiders" and "pre-fetching" can run "without fear of causing harm", and an unsafe action selected by URI parameters MUST be disabled on safe methods ([RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)). If GET consumed the token, the preview fetch would pair the crawler and burn the link.
- **Design.**
  1. The link is `https://stock-mover.onrender.com/pair#<token>`. The fragment is "dereferenced solely by the user agent" and never sent in the request ([RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.5)), so crawlers and server logs never see it.
  2. `GET /pair` serves the static SPA: one huge green button with a phone icon and an audio prompt.
  3. The tap sends `POST /api/driver/pair {token}`. A single atomic `update device_pairings set used_at = now() where token_hash = $1 and used_at is null and expires_at > now() returning driver_id` runs, then a `driver_devices` row is inserted with a fresh 256-bit token hash.
  4. The response sets `__Host-drv` (HttpOnly, Secure, SameSite=Lax). Renew it on each visit, because 6265bis recommends user agents cap cookie life at 400 days ([§5.5](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.5)).
  5. The manager's screen flips to "Paired: Android phone, 3:42 pm" with **Revoke** and **Send new link**. This is the §5.4 confirmation.
  Whether an installed Android PWA shares Chrome's cookie jar is **unconfirmed**. If the cookie is lost, the manager re-sends a link.

## D. Sending the link over WhatsApp

- **Click-to-chat (recommended for MVP).** `https://wa.me/<number>?text=<urlencoded>` takes the number in full international format with no zeros, brackets or dashes. `https://wa.me/?text=...` lets the sender pick a contact. ([WhatsApp FAQ](https://faq.whatsapp.com/5913398998672934)) The manager's own WhatsApp sends it. There is no API, no Meta account, no cost to us and no template review. The text is ours (Hindi plus the link). The server never needs WhatsApp credentials.
- **Cloud API (later).** It requires a Meta app and a business portfolio ([get started](https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started)). Outside a customer-service window, only **approved templates** can be sent, and review can take up to 24 h ([templates](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview)). Pricing is per delivered message by category and market, with India as its own market. Utility messages inside the 24-hour window are charged from 2026-10-01, and service messages get 1,000 free per number per month ([pricing](https://developers.facebook.com/docs/whatsapp/pricing)). New portfolios are limited to 250 unique users per 24 h until business verification or volume scaling ([messaging limits](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). **Decision:** click-to-chat now. Consider the Cloud API only for automatic "no ping in 2 h" nudges after the hackathon.

## E. Driver app tech

- **Geolocation.** Secure contexts only. The browser prompts for permission on `getCurrentPosition`/`watchPosition`, and how long a grant lasts is UA-dependent. The Permissions-Policy feature is `geolocation`. ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Geolocation_API)) Defaults are `enableHighAccuracy=false`, `timeout=0xFFFFFFFF` and `maximumAge=0`, so set `{enableHighAccuracy:true, timeout:20000, maximumAge:0}` and send `coords.accuracy` with each ping ([W3C Geolocation §7](https://www.w3.org/TR/geolocation/)).
- **No background location on the web.** The spec waits while the document is `hidden`. Watch updates are "exclusively for fully-active visible documents", and others are dropped ([W3C Geolocation §6.5](https://www.w3.org/TR/geolocation/)). `Geolocation` is `[Exposed=Window]` only, so service workers can't call it ([spec IDL](https://www.w3.org/TR/geolocation/)). Periodic Background Sync needs an installed app and a non-zero engagement score, and "the timing of synchronizations are not controlled by developers" ([Chrome docs](https://developer.chrome.com/docs/capabilities/periodic-background-sync)). Background Fetch is for downloads and uploads that outlive the page ([WICG spec](https://wicg.github.io/background-fetch/)). Neither provides location. Screen Wake Lock keeps the screen on, but it is released when the page is hidden ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)).
- **So:** Phase 1 means the driver opens the app and taps, every 1–2 h. The app can't wake itself, so reminders come from the manager's screen ("no ping in 2 h") through a WhatsApp click-to-chat nudge. Phase 2 means native Android. A `location` foreground service needs `FOREGROUND_SERVICE_LOCATION` and a granted COARSE/FINE permission, and it can't be started from the background without `ACCESS_BACKGROUND_LOCATION` ([FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types#location)). Background location is restricted by Play policy, and apps in the background get updates only "a few times each hour" ([background location](https://developer.android.com/develop/sensors-and-location/location/background)).
- **Install to home screen.** Chromium needs HTTPS and a manifest with `name`/`short_name`, 192 px and 512 px icons, `start_url` and `display`. A service worker is not required ([MDN installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)). Ship `/driver` as a separate manifest scope with its own icon (a truck).

## F. Design for low-literacy users

- **Primary guidance.** W3C COGA patterns: *Make Each Step Clear* (4.2.4), *Use Icons that Help the User* (4.2.7), *Use Clear Words* (4.4.1), *Keep Text Succinct* (4.4.5), *Separate Each Instruction* (4.4.9), *Provide a Login that Does Not Rely on Memory* (4.7.1), *Allow a Simple, Single Step Login* (4.7.2), *Provide Human Help* (4.8.1) ([COGA](https://www.w3.org/TR/coga-usable/)). WCAG 2.2: 2.5.8 Target Size (Minimum), AA, 24×24 CSS px; 2.5.5 Target Size (Enhanced), AAA, 44×44; 3.3.8 Accessible Authentication (Minimum), AA, no cognitive test such as a password; 1.4.1 Use of Color, A, colour must not be the only cue ([WCAG 2.2](https://www.w3.org/TR/WCAG22/)). The pairing link satisfies 3.3.8 and COGA 4.7.2 for drivers. Google's Next Billion Users team (first-party blog) recommends voice for low-literacy users, simple icons that need "no more than one tap", and short sentences when reading aloud ([blog.google](https://blog.google/technology/next-billion-users/voice-users-playbook/)). No first-party Material guideline specific to low literacy was found.
- **Patterns we'll use.** One shipment card and one big action per screen, with buttons at least 64 px (well above 44). Each state has a colour plus an icon plus a word: blue box "Pick up", yellow pin "Send location", green tick "Delivered". The destination is shown as a store photo and the city name. Quantity is a large numeral next to a box icon. Each screen has a speaker button that auto-plays once.
- **Hindi audio.** `speechSynthesis.getVoices()` lists the voices on the device and can be empty until `voiceschanged` fires ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis/getVoices)). The spec says "It is user agent dependent which voices are available", and `utterance.lang` takes a BCP 47 tag such as `hi-IN` ([Web Speech API](https://webaudio.github.io/web-speech-api/)). Whether Android Chrome ships a Hindi voice is **unconfirmed**. **Decision:** bundle about 8 pre-recorded Hindi MP3 prompts as the primary path. Use `speechSynthesis` with `hi-IN` only for dynamic text (city names), and only if `getVoices()` returns a `hi` voice.

## G. Phase 2 live map (brief)

- **Transport.** `@Sse()` returns an `Observable<MessageEvent>`. It is plain HTTP and Nest unsubscribes when the client disconnects ([Nest SSE](https://docs.nestjs.com/techniques/server-sent-events)). Gateways need `@nestjs/websockets` plus a platform adapter and listen on the HTTP port by default. Guards check messages, not the connection ([Nest gateways](https://docs.nestjs.com/websockets/gateways)). **Pick SSE:** the data flows one way (server → manager), and driver pings stay plain POSTs.
- **Tiles.** OSM's policy requires visible attribution, a valid Referer, honouring caching, and no prefetching or offline use. It has "no SLA" and may block heavy users ([OSM tile policy](https://operations.osmfoundation.org/policies/tiles/)). That is fine for a handful of managers. Use a commercial or self-hosted provider at scale.
- **Render Free.** It spins down after 15 min without inbound HTTP or WebSocket messages, and a cold start takes about 1 min. Each workspace gets 750 instance hours a month ([Render free](https://render.com/docs/free)). Pings every few seconds would keep the service up around the clock: about 744 h in a 31-day month, which is our arithmetic, and that leaves no room for a second service. A cold start would also drop live streams. Phase 2 needs a paid instance.

## H. Transfer request and transit data model

Existing tables: `runs` (`db.service.ts`), `store_locations` and `store_distances(a, b, distance_km, travel_days)` (`geo/geo.service.ts`), `stores_added` (`stores/stores.service.ts`), `stock_receipts` and `items_added` (`stock/stock.service.ts`), `ai_calls`. New tables, created with the same `create table if not exists` bootstrap:

```sql
users(id uuid pk, email text unique, name text, role text check (role in ('super_admin','store_manager')),
      location_id text null, password_hash text, active bool default true, created_by uuid, created_at timestamptz,
      check (role = 'super_admin' or location_id is not null))          -- one location per manager = "store assignment"
sessions(token_hash bytea pk, user_id uuid, created_at, expires_at, last_seen_at, user_agent)
drivers(id uuid pk, location_id text, name text, phone_e164 text, active bool, created_by uuid)
device_pairings(id uuid pk, driver_id uuid, token_hash bytea unique, created_by uuid, created_at, expires_at, used_at)
driver_devices(id uuid pk, driver_id uuid, token_hash bytea unique, paired_at, last_seen_at, revoked_at, user_agent)
transfer_requests(id uuid pk, from_location text, to_location text, status text, requested_by uuid, decided_by uuid,
      value_mrp int, needs_signoff bool, engine_move_id text null, reason text, created_at, updated_at)
transfer_lines(request_id uuid, sku_id text, qty int check (qty > 0), primary key (request_id, sku_id))
shipments(id uuid pk, request_id uuid unique, driver_id uuid, assigned_by uuid, assigned_at, picked_up_at,
      delivered_at, received_by uuid, received_at)
location_pings(id bigserial pk, shipment_id uuid, device_id uuid, lat float8, lng float8, accuracy_m real,
      taken_at timestamptz, received_at timestamptz default now())
transfer_events(id bigserial pk, request_id uuid, actor text, from_status text, to_status text, at timestamptz, note text)
```

**Lifecycle** is `requested → approved → assigned → in_transit → delivered → received`, with `rejected` coming from `requested` and `cancelled` from any state before `in_transit`. Each transition is one `update ... set status = $new where id = $1 and status = $expected returning *` (a stale click updates 0 rows) plus an insert into `transfer_events`, which feeds the manager's "In / Out" tracking. Driver taps move `assigned → in_transit` ("Picked up") and `in_transit → delivered`. The receiving manager confirms `received`. Any move worth more than ₹1,00,000 at MRP sets `needs_signoff`, and only the super admin can approve it. This follows the `rules.csv` approval rule noted in CLAUDE.md.

**"Nearest location".** Rank candidates with `select b, distance_km, travel_days from store_distances where a = $requester order by distance_km`. The table is kept by `GeoService.recomputeDistances()` (`apps/api/src/geo/geo.service.ts`), and the same ranking exists in memory as `GeoService.nearest()` / `StoresService.nearest()` (`apps/api/src/stores/stores.service.ts`, road km = haversine × `ROAD_FACTOR` 1.3, `apps/api/src/engine/params.ts`). Then keep only locations that hold the SKU and can give the quantity without breaking rules 1–4. Re-check this with the engine's validator (`apps/api/src/engine/validate.ts`) so manual requests also produce zero violations. Show the ETA from the `lead_times` route days the engine already uses (commit 4f51351), not from `travel_days`, so the two screens agree.

## Conflicts with current project rules

- **CLAUDE.md "Out of scope (say no)"** lists *Login, roles, … mobile layout, settings pages*. The driver app is mobile-only, and the user/driver admin screens are settings-like. That line needs rewriting.
- **CLAUDE.md "Decisions already made"** says *Approvals live in the browser (localStorage) … No auth, no users.* With users, engine-move approvals should move to the DB per user, or at least be keyed by user (`apps/web/src/data/approvals.tsx`).
- **CLAUDE.md "Hard constraints"** says *4 hours total … If it is not on the plan, do not build it.* This scope needs `docs/05-plan.md` and `TASKS.md` updated, plus a Decision-log line.
- **The five rules / "Zero rule violations".** Manager-initiated store-to-store requests are new moves and must pass the same validator. Rule 3 (in-transit counts) means approved and in-transit shipments must reach `runEngine()` as in-transit. Today `EngineInput` has no such field (`apps/api/src/engine/index.ts`).
- **Issue #19** proposes env users (`APP_USERS`, bcrypt), a stateless signed cookie, and "No sign-up, reset or roles". It is superseded: DB users, scrypt (OWASP ranks bcrypt as legacy), server-side sessions, roles. Keep its UX: a 401 goes to `/login?next=`, the error is "Email or password is wrong", and the 5-tries/min limit stays. Close #19 as superseded.
